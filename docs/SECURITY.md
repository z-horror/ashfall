# Безопасность и известные ограничения

> Это прототип. Он **не заявлен** как защищённый от всех читов, ботов, DDoS и компрометации. Ниже — что сделано, что не сделано и где риски.

## 1. Модель доверия

- Сервер — единственный источник истины: позиции, коллизии, урон, смерть, инвентарь, лут, двери, зомби.
- Клиент присылает только намерения: направление движения, угол прицела, id предмета, seq команды.
- Клиентские координаты, результаты атаки и содержимое контейнеров не принимаются.
- Общая физика (`shared/src/physics.ts`) используется и клиентом, и сервером; клиентское предсказание корректируется сервером.

## 2. Аутентификация и сессии

- Пароль: Node `scrypt` (N=16384, r=8, p=1), случайная соль 16 байт, формат `s1$salt$hash`. Сравнение — `timingSafeEqual`.
- Токен сессии: 32 случайных байта base64url; в БД хранится только SHA-256.
- Сессия: срок `SESSION_TTL_HOURS` (168 ч по умолчанию), проверяется на HTTP и WS.
- Гостевые аккаунты создаются с случайным именем/паролем; это удобно для тестов, но не для продакшена.
- Rate limit авторизации по IP: регистрация 8/мин, логин 12/мин, гость 20/мин; при неудачном логине добавляется задержка 250 мс.
- Токен на клиенте хранится в `localStorage` (`ashfall.session`). Для продакшена лучше HttpOnly/Secure cookie + CSRF-защита; текущий вариант уязвим к XSS на этом origin.

### Не реализовано

- восстановление пароля, смена пароля, 2FA;
- блокировка аккаунта после N неудач;
- отзыв всех сессий пользователя;
- проверка сложности/утечек паролей;
- OAuth/социальный вход.

## 3. WebSocket и валидация

- Первое сообщение — `auth`; таймаут 8 с, иначе закрытие 4001.
- `clientMessageSchema` (Zod) ограничивает типы, диапазоны, длины; неизвестные сообщения отклоняются.
- `maxPayload = MAX_MESSAGE_BYTES` (16 КиБ), дополнительная проверка размера.
- Token bucket: `MAX_MESSAGES_PER_SEC` (90/с) на соединение; при превышении — `RATE_LIMIT`.
- `seq` дедуплицирует критичные действия (атака, инвентарь, двери, respawn).
- Игровые проверки: дистанции, кулдауны, владение предметом, вес/слоты, LOS для дальнего боя, патроны, состояние (жив/мёртв).
- Транзакции PostgreSQL + `FOR UPDATE` для инвентаря/контейнеров/смерти; это защищает от дублирования предметов при гонках и сетевых ретраях.
- Ошибки клиенту приходят как `error`/`notice`, без стектрейсов и внутренних деталей.

### Риски

- **Origin не проверяется** на WS upgrade. В проде нужно ограничить allowlist origin.
- **CORS** в dev открыт для любого Origin (`NODE_ENV !== production`); в production заголовки не выставляются, но reverse-proxy может добавить свои.
- **Нет TLS** в dev; в Docker отдаётся HTTP. Для интернета обязателен HTTPS/WSS reverse-proxy (Caddy/Traefik/nginx) и Secure cookies (если перейдёте на cookie).
- **DoS:** нет глобального лимита соединений на IP, нет защиты от медленных клиентов, память под сессии/игроков не ограничена жёстко. Рассмотреть `ws` rate limit на upgrade, лимит соединений, таймауты.
- **Aimbot/triggerbot/macro** сервер не обнаруживает; можно логировать аномалии (частота попаданий, скорость поворота) и добавлять эвристики.
- **Клиент может врать aim** в пределах допустимого угла; сервер проверяет только геометрию и кулдаун.
- **Нет античита памяти/браузера**; это браузерная игра, клиент полностью под контролем игрока.
- **PvP и полный лут** — намеренно жёсткие правила; риск социального грифтинга.
- **SQL-инъекции** исключены параметризованными запросами; имена таблиц/колонок в репозитории берутся из фиксированных union-типов, не из пользовательского ввода.
- **Утечка секретов:** `.env` в `.gitignore`; в Docker Compose пароли БД по умолчанию — только для локального запуска. Не использовать эти значения в проде.
- **HTTP-заголовки:** сервер выставляет `content-type`, `cache-control`, `nosniff`; nginx добавляет `X-Frame-Options`, `Referrer-Policy`, `X-Content-Type-Options`.
- **CSP** отсутствует; Vite dev требует inline/eval. Для продакшена добавить строгий CSP после аудита.

## 4. Целостность игровых данных

- Сервер не принимает координаты/урон от клиента.
- Дроп при смерти выполняется одной транзакцией: выборка инвентаря `FOR UPDATE`, вставка ground_items, удаление character_items, обновление deaths/status.
- Подбор: `DELETE ... RETURNING` + вставка в инвентарь; два клиента не получат один предмет.
- Контейнеры инициализируются лениво под блокировкой строки; повторное открытие не создаёт новый лут.
- Двери/пропсы сохраняются при изменении; повторный запрос с тем же seq игнорируется.
- Seed мира проверяется по `world_meta`; смена seed без очистки БД блокируется.

### Остаточные риски

- Гонки между несколькими процессами сервера не поддерживаются: один процесс — один мир. Горизонтальное масштабирование потребует внешней блокировки/шардирования.
- Падение процесса между in-memory изменением и записью в БД: критичные операции стараются писать в БД до подтверждения, но позиция/статы сохраняются периодически (потеря последних секунд возможна).
- Лут, выпавший при смерти, может быть подобран другим игроком до сохранения события — это нормальная механика, не баг.
- Смерть/респавн офлайн-игрока: при следующем входе персонаж может быть уже возрождён; см. `Simulation.join`.

## 5. Приватность

- Хранятся: имя, хеш пароля, игровые действия, позиции, инвентарь, IP не сохраняется в БД (только в памяти для rate limit).
- Чаты сохраняются в `world_events` (payload) — при необходимости добавьте retention/удаление.
- Нет аналитики/трекеров.
- Не используйте реальные пароли в прототипе.

## 6. Рекомендации перед публичным запуском

1. TLS/WSS + reverse-proxy; HSTS.
2. Origin allowlist на WS; ограничение соединений/IP.
3. HttpOnly/Secure cookie-сессии + CSRF или короткоживущие токены с refresh.
4. CSP, запрет inline где возможно; санитизация чата на клиенте (сейчас используется textContent).
5. Ограничения на размер/количество аккаунтов, капча для регистрации.
6. Метрики/алерты: p95 tick time, число соединений, ошибки БД, latency.
7. Бэкапы PostgreSQL и проверка восстановления.
8. Логирование подозрительной активности (аномальная частота атак, телепорты клиента невозможны, но aim/скорость поворота можно анализировать).
9. Аудит зависимостей (`npm audit`) и обновление по мере выхода патчей.
10. Разделить dev/prod секреты; не использовать значения из `.env.example`.

## 7. Ответственное раскрытие

Если найден баг безопасности — не публикуйте его публично. Создайте приватный issue/сообщите владельцу репозитория с шагами воспроизведения, Impact и предложением фикса.
