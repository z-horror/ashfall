# Эксплуатация и развёртывание

## 1. Локальный Docker

```bash
cp .env.example .env
docker compose up -d --build
docker compose ps
curl http://localhost:8080/api/health
```

- `client` (nginx) слушает `8080`, проксирует `/api` и `/ws` на `server:3000`.
- `server` автоматически применяет миграции при старте (`MIGRATE_ON_START=true`).
- `db` (PostgreSQL 16) доступна на `127.0.0.1:5433`; данные в volume `ashfall_pgdata`.

Логи:

```bash
docker compose logs -f server
docker compose logs -f client
docker compose logs -f db
```

Остановка/сброс:

```bash
docker compose down            # данные БД сохраняются
docker compose down -v         # полный сброс мира (необратимо)
```

## 2. Production-чеклист

- [ ] TLS/WSS через reverse-proxy (Caddy/Traefik/nginx), HSTS.
- [ ] Сильные пароли БД, отдельный пользователь, network isolation, порт БД не наружу.
- [ ] `NODE_ENV=production`, `MIGRATE_ON_START` по процессу деплоя.
- [ ] Ограничение Origin на WS (сейчас не реализовано), лимиты соединений/IP.
- [ ] HttpOnly/Secure cookies или короткоживущие токены (сейчас localStorage).
- [ ] CSP и security headers (частично есть в nginx).
- [ ] Бэкапы PostgreSQL + проверка restore.
- [ ] Мониторинг: health, p95 tick, память, WS-соединения, ошибки БД.
- [ ] Ограничение ресурсов контейнеров (CPU/RAM), restart policy.
- [ ] Ротация логов; `[sim] saved ...` в prod приглушить.
- [ ] Не менять `WORLD_SEED` на живой БД.
- [ ] Протестировать рестарт сервера с реальными игроками.

## 3. Один процесс — один мир

Сервер держит симуляцию в памяти. **Нельзя** запускать несколько инстансов server против одной БД: это приведёт к конфликтам состояния/дублям. Для масштабирования нужны:

- шардирование по мирам/регионам;
- вынос состояния в Redis/БД с блокировками;
- отдельный матчмейкинг/лобби;
- либо один мощный процесс с оптимизацией.

## 4. Бэкапы

```bash
docker compose exec -T db pg_dump -U ashfall -d ashfall -Fc > backup_$(date +%F_%H%M).dump
# restore (на пустую БД):
docker compose exec -T db pg_restore -U ashfall -d ashfall --clean --if-exists < backup.dump
```

Проверяйте restore на тестовой БД. Бэкап без проверки восстановления бесполезен.

## 5. Обновление схемы

- Только новые файлы `database/migrations/002_...sql`, `003_...sql`.
- Не редактировать применённые миграции.
- Раннер записывает имя файла в `schema_migrations`.
- Перед миграцией — бэкап.
- Откат: отдельная down-миграция или восстановление из бэкапа (автоматического down нет).

## 6. Смена мира

1. Остановить сервер.
2. Сделать бэкап, если данные нужны.
3. `docker compose down -v` (или очистить таблицы/создать новую БД).
4. Изменить `WORLD_SEED` в `.env`.
5. Запустить `db`, миграции, сервер.
6. Убедиться, что `world_meta.world_seed` соответствует новому seed.
7. Обновить документацию/скриншоты.

## 7. Диагностика

| Проблема | Действия |
|---|---|
| `/api/health` 503 | Проверить БД, `DATABASE_URL`, логи server/db |
| WS не подключается | Проверить прокси `/ws`, upgrade headers, timeout 90s, firewall |
| Клиент грузится, но пустой | Проверить `/ws`, welcome/chunk в devtools, ошибки JS |
| Seed mismatch | Вернуть seed или осознанно сбросить мир |
| Высокий CPU | Профилировать тик, число зомби, LOS, снапшоты; включить метрики |
| Высокая память | Число игроков/сущностей, размер чанков, утечки Phaser-объектов |
| Предметы дублируются | Проверить транзакции, seq, конкурентные запросы; логи `[sim]` |
| Клиент «резинит» | Сравнить predicted/self, коллизию, закрытые двери, RTT |
| Docker build падает | Проверить lock-файл, Node 22, контекст, `.dockerignore` |

## 8. Логи и события

- `world_events` — аудит важных игровых событий; для продакшена нужен retention (например, 30 дней) и ограничение размера JSON.
- Чат сейчас пишется в `world_events`; при необходимости добавьте модерацию/удаление.
- Не логируйте токены/пароли/полные заголовки авторизации.
